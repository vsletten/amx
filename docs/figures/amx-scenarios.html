amx · what it makes possible — six things you get by putting agents on email, each already running in the prototype

Cross-organization work with people in the loop, control at the transport, and a record that stands on its own. None of it requires a shared platform, an API integration, or a dashboard.
1Agents in different companies work a task, with a person on CC
Two organizations exchange a structured task with no shared platform and no API keys: the address is DNS MX and the identity is a per-agent signature. A person on CC reads it in Gmail, and when they hit Reply, the answer lands on the right task because the correlation token lives in the address.
Prototype scenarios S01, S02, S05 · agents at northwind.test and contoso.test, plainmail.test as the "Gmail" stand-in
2People approve what an agent is about to send, from their own inbox
Outbound mail that matches a hold rule is not sent. It sits in a folder the person already has, in Roundcube, Outlook or a phone. Moving it to Approved releases it, signed at that moment. Moving it to Rejected tells the agent its task is canceled. No approval dashboard was built.
Prototype scenario S06 · approve and reject from the mail client
3Busy or offline agents slow their callers down, without any code
An agent over its watermark answers the SMTP transaction with a temporary failure. Every mail server already knows what to do with that. The message is never lost and nobody writes a retry loop, a queue, or a webhook. Refusing work permanently is a bounce that carries the reason.
Prototype scenarios S04a, S04b · watermark backpressure and a gateway outage
4Bad mail is refused at the door, and a rogue agent is revoked in DNS
Policy runs before the message is accepted, so nothing untrusted is stored or shown to an agent. The sender learns why in a normal bounce. Because each agent has its own published key, one agent can be shut off by deleting one DNS record, and that revocation is honored by every receiver.
Prototype scenarios S03, S05, S07, S09, S12 · rejection, revocation, loop guard, closed task, unsigned human lane
5Prompt injection cannot gain authority, and suspect input is held
Content is evidence, never instruction: nothing in a message body can change what its sender may do. One typed-model call at the gate asks whether the text tries to steer the agent, whether the human and machine parts agree, and what it really intends. Suspect mail from a person still arrives, but the agent's response waits for a human.
Prototype scenarios S13–S17 · injection, parts disagree, intent smuggling, judge outage, off/observe/enforce
6A tamper-evident record of everything your agents said and were told
Every accepted inbound and every released outbound message is a text file with a SHA-256 linked to the previous entry. Editing one entry breaks the chain and the tool says where. The transcript of what your agents agreed with someone else's agents is an mbox you can hand to a lawyer.
Prototype scenarios S08, S10 · tamper detection and recovery, replay dedupe
Every scenario above is an automated end-to-end test in the amx prototype (Python gateway on Postfix + Dovecot, three .test domains, Roundcube as the person's client). Open source, Apache-2.0.
